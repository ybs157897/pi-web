# Pi Web 项目增强提示词

用途：交给负责开发本仓库的编程 Agent。复制下方正文即可使用。它要求实现和验证项目能力；不要把整份开发任务书注入应用内的每一次模型请求。

配套文件：[运行时系统提示词](runtime-system.md)、[源码依据与使用说明](sources-and-integration.md)。基线核对日期：2026-10-19；执行时重新核对当前工作树。

---

你负责增强当前 Pi Web 项目，使它成为程序员可以持续使用的 AI 开发工作台。项目基于 Pi Durable 执行与持久化内核，参考 DSH 的交互与协作方式。目标是让它可靠完成代码理解、开发、问题定位、修复、验证和环境准备，并支持 Skill、MCP、子 Agent 与团队协作。

请在现有架构上实现可验证的改进。先核实事实，再解决实际缺口。提示词指导模型决策，工具与运行时负责执行约束、持久化、幂等和权限；不能用提示词替代工程机制。

## 一 工作边界和当前基线

默认“当前项目”指本次绑定的仓库和工作目录，不反复询问项目位置。先读适用的仓库指令、package.json、锁文件、README、docs/architecture.md、docs/families.md、docs/parity.md，以及相关实现和测试。工作树可能包含其他会话的改动，保留它们，围绕本任务做最小修改。提交、推送、合并、发布按用户已有授权分别处理。

当前基线需要保留并重新核实：

- TypeScript、Hono、React、Vite；Pi Durable、Pi AI、Pi Codemode、Pi MCP 锁定为 1.3.0，使用 SQLite。Durable README 标注 Experimental；它不是带 beta 后缀的版本号。用户所说的 beta Durable 指这条新运行时路线，不要把它当作旧 Pi CLI，也不要凭名称推断成熟度。
- 应用会话对应 Pi Conversation，Entry 是历史记录，Task 是持久任务，Doc 承载可恢复状态；应用元数据和浏览器草稿各有自己的所有者。
- 已有读写编辑与 shell、队列和插入消息、停止、分叉、压缩、目标、计划、问答、普通子 Agent、团队看板、Agent Preset、自动化、code mode 和 MCP 相关实现。已有代码不等于所有场景都已验收。
- 已接入内置 skill-creator、Markdown Skill 发现/按需加载、受控保存和校验；工作区根 AGENTS.md 按请求自动注入，子目录指令仍按操作路径逐级读取。Preset 的 instructions 是角色配置，不等于 Skill；源码内 registry.install 也不等于用户可安装插件。
- 问题单闭环和可复现验证环境是后续产品方向，必须按实际接入状态展示，不能在提示词或 UI 中宣称已经可用。

先形成简短能力清单：功能、上游支持、项目接入、模型可见、权限约束、测试证据、缺口。不要把历史文档中的“已通过”当成本次验证结果，也不要为了调研进行无关重构或升级依赖。

## 二 提示词工程与能力注册

已有可维护的默认提示词组合入口：`src/server/work-policy.ts` 与 `src/server/prompts/runtime-core.md`，通过 Pi Extension/section 注入并保留 Agent instructions。后续增强先核对这条链路，不重复建立另一套执行内核或只编辑未被读取的文档副本。

将内容分成以下层次：

1. 稳定核心：产品身份、任务推进、证据要求、授权边界、工程质量。
2. 会话事实：实际 workspace/cwd、操作系统、模型、访问模式、角色、plan/goal 状态、code mode、可用工具、Skill 目录与集成状态。
3. 项目指令：按已实现的查找范围加载 AGENTS.md，记录来源、作用域和版本；目录级指令只作用于对应目录。明确用户级和项目级来源优先级，避免加载任意祖先目录或其他项目的私密规则。
4. 按需内容：当前 Skill 正文、任务相关资料、问题单事实、环境与验证证据。

能力说明必须来自实际 registry 和当前会话过滤结果。模型可见工具、可被 codemode 嵌套调用的工具、deferred 工具和不可用工具必须区分。稳定核心不重复完整工具 schema，不硬编码会过期的模型名、工具列表和能力承诺。

保留 Pi 已有的 code mode、plan、goal、team sections；避免重复注入、相互冲突或由 Preset 覆盖掉必要的运行时约束。对主 Agent、普通子 Agent、Team Lead、Teammate 分别组合适当上下文，不把主 Agent 的所有管理权限和职责机械复制给成员。

提供可检查的提示词来源、版本和能力摘要，方便定位“为什么模型认为自己有这个工具”。调试信息脱敏，敏感配置不进入模型上下文。提示词的稳定性需要行为评测，不能只测试某个字符串是否出现。

## 三 Pi 原生能力与 Durable 稳定性

以锁定依赖的 README、类型和实现为准，区分 Pi 的模型调用层、Durable 运行时、CodingTools、CLI 资源加载器和本项目 Host 层。

重点检查并补齐：

- 消息接纳、排队、steer、停止、分叉、压缩、重连和重启之间的状态转换。重试发送复用同一个 requestId，不能因为网络超时重复提交用户意图。
- 停止当前工作与撤回队列是不同操作；保持当前项目保留排队输入的约定。检查停止对普通子任务和后台团队成员的不同影响，不能留下 UI 宣称停止、后台继续执行却不可见的情况。
- 前端通过完整快照恢复当前视图；不要把现有 SSE 重连描述成尚未实现的持久游标重放。工具调用、结果和嵌套调用按稳定 ID 关联。
- Durable 的 replay safe 标记不自动提供外部副作用的 exactly-once。逐类审核文件、shell、MCP、网络写入、问题单更新与发布操作；使用稳定幂等键、持久回执或执行后状态核查。状态不明的外部写入不得盲目重试。
- 通过 Doc/事务保存跨轮目标、看板、待回答问题和执行回执，不能仅从被压缩的聊天文本重建事实。区分已接纳、执行中、等待、取消、失败、工具返回错误、模型停止和业务完成。
- 压缩保留用户目标、已授权动作、关键决策、当前改动、待办、问题与环境标识、证据位置和恢复入口。摘要是续接线索，不是外部操作成功的凭据。
- 重启前后重新建立模型、工具、环境和扩展注册；验证缺失或变更时的明确失败路径。遵守所用存储的单写者约束；不把本地 SQLite 恢复宣传成多进程调度、分布式租约或高可用接管。
- 区分进程崩溃恢复与断电耐久性；当前 SQLite WAL/NORMAL 配置不能保证主机故障时保住最近所有提交。数据库和依赖升级前检查迁移与回滚限制，不把上游 Unreleased 的任务、唤醒或 telemetry API 当作 1.3.0 已有能力。
- 检查当前空的 onReport 回调，按严重度保留可诊断的内部错误与关联标识；存储级故障不能被当成普通工具失败吞掉。诊断脱敏且有体积上限，不无限堆积日志。
- 为等待、工具超时、取消、后台任务清理、重试和目标续跑设置可解释的边界；认证失败、权限拒绝与普通暂时性错误分别处理。禁止静默切到演示模型或其他供应商伪造成功。

## 四 内置 Skill 创建能力

交付的是“Skill 方法论 + 可执行的资源管理工具 + 确实可加载的产物”。只添加一段告诉模型去写 SKILL.md 的提示词，不能算完成。

实现与本项目相适配的 Skill 生命周期：发现、列举、读取、创建或更新、校验、启停或重载、诊断。工具名称可以沿用项目命名规范；设计稿中的名称不得在工具注册前暴露为现有能力。

默认新 Skill 放在当前工作区的 `.agents/skills/<name>/SKILL.md`，兼容发现 `.pi-web/skills/`。当前版本已提供四个 skill_* 工具和内置创建器，先检查它们再做增强，避免重复实现。用户级来源尚未接入，不擅自写入用户的 Codex/Pi 全局目录；同名来源使用完整 ID，不隐式覆盖。

内置 `skill-creator` 应能完成：

1. 从任务提炼明确用途和触发条件；先判断已有 Skill 能否复用或局部修订。
2. 生成最小有效目录；SKILL.md 的 YAML frontmatter 至少有 name 和 description，正文包含适用条件、操作约束、必要输入、执行方法、验证与失败处理。
3. 只在有用途时添加 scripts、references、assets；正文按需指向它们。Skill 描述要短而准确，不用“所有开发工作都必须使用”等宽泛触发词。
4. 校验命名、frontmatter、引用、脚本入口、依赖和路径范围；原子保存，覆盖已有版本前提供差异，并按当前授权与版本冲突规则处理。
5. 将新版本纳入当前会话可发现目录，说明对正在运行会话何时生效；校验失败保留可修复草稿，不能显示“已启用”。
6. 用一个真实请求验证发现、读取、执行和结果；对容易误触发的 Skill 加一个不应触发的案例。脚本在隔离样例中实际运行，不能只通过文本检查。

目录常驻上下文仅包含名称、简短描述和真实来源。决定使用某个 Skill 后再读取其正文；引用资料按需要加载。Skill 是工作方法，不授予额外文件、网络、凭据、团队或外部写入权限。创建 Skill 不自动安装依赖或执行其中脚本。

最小格式示例：

```markdown
---
name: verify-issue
description: 复现并验证一个已关联代码版本和环境的问题；用于修复前后行为对照。
---

使用问题单中的预期行为、复现步骤和已选环境。
先核实环境与版本，再执行复现；保存命令、退出码与相关产物。
区分问题仍存在、修复通过、环境阻塞和证据不足。
只有取得修复前后对照证据，才报告该问题验证通过。
```

这个例子仅展示 Skill 格式，不表示问题单工具已经实现。

## 五 MCP 与 code mode

保留现有 stdio、Streamable HTTP、工具命名和 exposure 路径，核实每个会话最终可见和可调用的工具。

- `direct`、`deferred`、`codemode`、`hidden` 是工具暴露策略，不是权限级别。当前 `codemode` 和 `deferred` 都可能由 tool_search 加载；关闭 code mode 不代表关闭所有 MCP 工具。
- `codemode` 执行的是 QuickJS 中的工具编排脚本；嵌套工具仍可能产生文件或网络副作用。沙箱隔离 JavaScript 不等于隔离全部宿主工具和 MCP 服务器。
- MCP 配置现为只读导入、启动时读取，页面刷新不等于重载服务器。若增加编辑、重载、OAuth、资源或 prompts 支持，分别实现完整生命周期和错误反馈，不能依据依赖有 API 就宣称产品已接入。
- 验收分开检查：端点可达、协议连接、工具登记、模型实际调用、预期外部结果。外部服务返回错误不能被包装成成功文本。
- 配置字段、连接错误、工具输出和诊断各自检查脱敏；只证明配置 DTO 不返回 headers/env，不能推出所有路径都不泄密。
- MCP 服务器进程及远端服务的执行权限单独治理，不能假定自动受会话 shell 的 workspaceWrite 沙箱限制。

## 六 子 Agent 与团队模式

保留两种不同的调用方式，并让模型和用户知道何时选择：

- `subagent({ task, label? })`：独立子会话、前台等待答案，适合边界清楚的单次研究或执行任务。默认不继承父消息，必须提供自足任务上下文。
- Team：Lead 调用 `spawn_teammate` 创建后台成员，通过 `send_message`、`list_agents`、`wait_agent`、`interrupt_agent`、`team_task_create`、`team_task_list`、`team_task_get`、`team_task_update` 协作。当前没有独立团队开关；无 Preset 时默认装配团队扩展，使用选定或默认 Preset 时必须在其中包含 `team` 扩展及所需工具。已有成员或看板内容后 UI 才出现入口。

让用户说“开启团队模式，拆成实现与验证两个任务”时，模型能够先确认当前真实工具面，按需启动团队并创建清晰任务；工具不可用时准确解释是 Preset、权限还是注册缺失，不能虚构 `/team` 指令。

团队可靠性要求：

- 主 Agent 负责理解目标、拆分、整合和验收；成员接到完整任务、文件范围、依赖、权限和交付要求。简单工作直接处理，不为展示团队强行拆分。
- 普通子会话与 teammate 默认继承父配置；Teammate 的 fresh 不继承消息，fork 只继承最近已完成回合前缀。必要任务上下文仍显式传递。
- 成员共享工作目录；write_scopes 是提示性范围，不是文件锁。分配不重叠写入范围，对共享文件串行处理。不能覆盖其他成员尚未提交的改动。
- 看板更新使用最新 revision，冲突后重新读取并重做决策。任务 ready 不会自动启动负责人，必须显式派发。
- `send_message` 成功只代表接纳；`inactive` 只表示当前无回合执行。先 list，再唤醒需要工作的 inactive 成员，再等待后续变化；noProgress 和超时不能当完成。
- 完成需要任务状态、实际产物和验证证据一致。后台成员不会因为 Lead 停止就自动全部取消；实现清晰的停止范围、重启恢复和失败清理。
- 对递归深度、成员数、并行度、消息量和重试设置 Host 约束，权限不能靠子 Agent 提示词“自觉遵守”。

## 七 程序员工作流与问题单

产品定位覆盖“定位问题—修复—验证—交付”。后续问题单功能应沿用现有 Conversation/Task/Doc 能力，保留稳定业务标识与版本，避免靠聊天标题或最近几条消息关联。

问题记录至少应能关联：来源和外部 ID、标题、预期与实际行为、复现条件、相关仓库及代码版本、环境配置版本、附件和日志、修复任务、验证记录、阻塞原因。

修复工作流：先阅读问题与相关代码，形成最小复现；根据证据确认根因，实施适量修复；用原复现路径验证修复后行为，并执行受影响的回归检查。无法复现、环境阻塞和产品预期不清要分别记录，不能用“已修复”覆盖这些状态。

把修复执行和验证结论分开。独立验证 Agent 根据预期行为与证据检查结果，不能只复述实现者的完成声明；小改动不强制额外创建 Agent。验证结果至少区分通过、失败、环境阻塞、未执行、证据不足。

外部问题单同步需保留来源版本、幂等键和状态映射；Agent 提交修复不自动意味着可以对外评论或关闭问题。后续接哪个平台应由实际需求决定，不提前绑定虚构接口。

## 八 验证环境配置与集成

设计可复现的环境配置，而不是只保存一个 URL 或命令字符串。一个环境应能描述：类型与版本、代码版本、运行时/包管理器、依赖安装、启动和健康检查、端口与服务地址、测试数据、验证入口、日志产物、清理方式，以及凭据引用。

优先支持用户实际需要的一种环境形成闭环，再扩展 local、container、remote 或 preview；尚无后端的类型不显示为可用。默认复用已确认环境，不为每次检查重建工作区或打断已有服务。

环境准备、检查和问题验证分开记状态。连接不上服务、凭据失效、依赖安装失败属于环境证据，不能直接判断功能有缺陷，也不能标记修复通过。每次验证绑定代码与环境的具体版本，避免在旧服务上验证新代码。

密钥只以受控引用保存，按需注入进程；不写入提示词、Skill、日志或前端 DTO。宿主工具实际落实访问范围、进程所有权、网络策略和清理；验证工具不能通过另一条执行通道绕开会话限制。

## 九 验收与交付

先修实际高风险断点，再补能力链路。问题单与环境集成按用户明确的阶段实施；规划内容在完成前保持未启用，不以占位 API、演示数据或假成功替代。

按改动触面选用现有 typecheck、test、build、smoke、真实工具和真实模型脚本。确定性测试验证状态机与故障场景，真实模型验证工具选择和指令遵循，真实 UI 验证用户操作；三者分别报告。执行真实模型测试前核对适用的仓库与任务约束，特别是 docs/families.md、docs/parity.md 记录的 DeepSeek 验收要求；脚本使用默认模型不代表可以忽略这些限制，不擅自换模型或修改凭据。

最低行为验收集合：

1. 普通开发任务能检查、修改并验证；只分析任务不会写入。
2. 幂等重发、队列编辑与执行竞争、停止后队列保留、刷新与进程重启不会重复用户意图。
3. 副作用边界发生崩溃后，能查回执并安全恢复，不能仅测试“历史还在”。
4. 压缩和续跑保留目标、授权与待办，未完成任务不会误报完成。
5. 新建 Skill 能被发现并实际执行；坏 frontmatter、越界引用和并发覆盖能正确诊断。
6. MCP 断连、工具错误、deferred 加载和 code mode 切换的结果真实可见；只读会话无法经嵌套调用获得写权限。
7. 普通子 Agent 和团队分别验证；覆盖任务冲突、消息接纳但未处理、inactive、noProgress、成员失败和重启恢复。
8. 问题单与环境功能启用时，用一个真实或隔离样例完成修复前失败、修复后通过、关联证据回填；环境失败不得误判通过。

对提示词建立少量可重复场景，比较改动前后的工具误用、虚构能力、遗漏验证、重复副作用和任务中断续接。固定案例与版本，多次采样高风险行为；不声称一次通过就永久稳定。

交付说明具体改动、实际运行的验证、未通过或未执行项、仍存限制。只对证据覆盖的能力宣布完成。
