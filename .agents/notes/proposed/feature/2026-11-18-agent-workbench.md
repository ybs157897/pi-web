# Agent Note: Agent 工作台——单入口对话、智能体团队与裁决收件箱

Status: proposed

原型：`.data/prototypes/work-items-v5.html`（gitignored，仅评审用）。本 note 记录产品形态与实施边界；原型交互是验收基准。

## Proposal

### 问题

日常开发是碎片化的：写代码、查日志分析问题、整理需求同时发生。多开 Agent 会话时，人要在多个窗口间切换，记不住每个会话做到哪、在等谁、谁在跑。人脑的上下文有限，过载不是任务太多，而是状态持有成本太高。

现有 pi-web 已有对话、子智能体、团队任务、交互提问和轨迹，但缺少三层：任务状态不脱离会话存在、执行者不可见、需要人介入的事情没有统一入口。

### 产品形态

1. **首次引导**：只做工作空间选择——列出现有工作空间或直接命名新的，一步进入。不做 runtime/Codex 配置（pi-web 自身就是核心引擎）。
2. **唯一入口：Agent 对话**。空态是输入框 + 示例卡；输入 `@` 弹出分组菜单（成员 / 电脑 / Bot 与任务），选中的智能体在输入框里是一颗实体胶囊，发送后气泡中也保留。
3. **派发与接单**。发送后由主 Agent 选择或遵从 `@` 指定派给子智能体；主线只回一句「已收到，本 bot 开始执行」，随后是一张召唤卡，卡片只显示状态：进行中 / 已结束。主线不输出分析正文。
4. **子智能体会话**。点召唤卡进入：任务来源（来自主 Agent）、执行步骤、完整分析正文、交付结果；底部可以继续与该智能体对话。子会话是可返回的详情，不是并列的工作入口。
5. **收件箱**。按会话分组的裁决与结果，类型标签为选择 / 确认 / 审阅 / 异常 / 结果。点开是真实邮箱式的完整信件：工具栏（返回/回复/稍后/归档/回到对话）、邮件头（发件人 pi-web Agent、收件人、时间）、完整正文、底部固定对话条。底部回复直接发到对应会话；「展开到对话」回到主线并高亮对应召唤卡。
6. **Bot 页**。参考 `feat/module-bot-team` 的三栏控制台：左侧 Bot 名册（主 Agent 作为 lead 卡 + 子智能体行，带状态点），中间选中 Bot 的会话，右侧详情（角色、模型、权限、最近运行、技能）。名册里可切换，也可直接继续对话。

### 信息规则

- **进收件箱**只有五类：需求有歧义、高影响/不可逆、范围冲突、无法自动验收、结果待验收。
- **不进收件箱**：有默认值的技术选择、能靠测试判定的实现细节、可事后更正的改动、单纯进展通知。这些由 agent 自己处理，在会话里一句话回报。
- 每封邮件展开后第一块是「为什么找你」，写明属于哪一类、为什么默认值说服不了自己。
- 主线只显示状态与接单确认；正文、步骤、结果只在子会话与收件箱里展示。
- 结果型邮件带验收：通过则归档，退回则回到对应子会话返修。

### 内部机制

- **主 Agent**：读需求、拆任务、建依赖、决定派给谁、决定何时请示；不执行具体工作。
- **子智能体**：独立上下文与工作目录执行单一职责任务；按模块或领域分工（日志/导入/时间只是示例）。
- **工作项**：类型（build/investigate/decide）、目标、约束、验收、依赖、证据指针、等待对象；状态为待澄清、就绪、进行中、待验证、需要人、已结束。任意时刻必须有唯一等待对象。
- **调度**：依赖满足才派发；并发、重试、租约与心跳；超时与阻塞单独可见（只读抽屉）。
- **证据门**：程序验证优先（测试/检查/构建），独立审查可选；证据不足是独立状态，不显示为通过。
- **收件箱投递**：复用现有 Interaction 协议（callId 幂等、answer/cancel 路由）；对话回复与邮件按钮写同一个 Interaction，先到先得，另一侧同步关闭。

### 与现有实现的关系

- `InboxPage.tsx` 当前是静态 Gmail 演示、与 Interaction 零连接、自建 `--mail-*` 调色板；改造为真实裁决邮箱，样式回到 `vendor/dsh-theme` token。
- `MainPage` union 增加 Agent 之外的 Bot 视图；沿用现有无路由架构与懒加载。
- 子智能体会话复用后台 subagent / team 会话，不新建执行体。
- 收件箱条目复用 `Interaction`（question / plan-review / approval），结果型邮件新增一种投递类型。
- 视觉沿用 dsh-theme、`dsh-client-ui-primitives` 与现有 Inbox 外壳；不引入新 UI 库。

### 分期

**阶段 1：收件箱真实化。** 工作项数据模型（文件或库）+ 收件箱列表与详情改为真实数据 + Interaction 接入 + 为什么找你/证据/跳转。验收：能完成一次真实裁决并关闭对应 Interaction。

**阶段 2：召唤与子会话。** 派发卡（进行中/已结束）+ 子智能体会话视图 + 主线接单确认。验收：从对话发任务到子会话产出结果，全链路可点。

**阶段 3：入口与名册。** 首次引导（工作空间选择）+ `@` 提及（含胶囊）+ Bot 页。验收：新用户可完成引导并从空态发起第一单任务。

## Acceptance criteria

1. 新装首次打开只出现工作空间选择，无 runtime/Codex 配置；选择后进入 Agent 对话。
2. Agent 对话是唯一可发任务的地方；收件箱与 Bot 页没有新建任务入口。
3. 输入 `@` 能选择智能体，选中项以胶囊形式留在输入框；发送后气泡保留胶囊。
4. 发送后主线只出现「已收到，本 bot 开始执行」与一张召唤卡；卡片只显示进行中/已结束。
5. 点击召唤卡进入对应子智能体会话，能看到任务来源、步骤、正文与结果，并能继续对话。
6. 收件箱按会话分组，条目带类型；点开是完整邮件（工具栏/邮件头/正文/底部对话条）。
7. 收件箱底部回复能写回对应会话；「展开到对话」能回到主线并定位到对应召唤卡。
8. 收件箱只接收五类事；其余情况不产生邮件，只在会话内回报。
9. 结果型邮件支持验收；验收后归档，不再出现在待处理。
10. 所有界面同时支持明暗主题，颜色只使用 dsh-theme token。

## Risks

- **InboxPage 重写回归**：现有页面是纯演示、无真实数据，重写不会破坏现有行为，但会替换掉用户已看到的视觉；需要保留外壳与视觉基线。
- **提示词与上下文膨胀**：主 Agent 只派发、不执行，要求提示词明确职责；否则会退化成单会话包办。
- **并发与租约**：子智能体并行时需要 lease/心跳/重试，否则任务会被重复领取或永久卡住；早期可先用单进程队列，保留协议形状。
- **@ 提及与聊天输入的兼容**：contenteditable 替换 textarea 会影响输入法、粘贴与快捷键；需要覆盖中文输入法与纯文本粘贴的测试。
- **参考实现的许可**：`plane` 为 AGPL-3.0、`itsaplan` 为 AGPL-3.0、`huly` 为 EPL-2.0，只借鉴交互与语义，不复制代码；`kaneo`（MIT）与 `circle`（MIT）可用于组件级参考。
- **原型与实现的漂移**：原型在 `.data/`（gitignored），需在实现前把关键决策同步到本 note 或 subsystem 文档，避免后续无法追溯。
